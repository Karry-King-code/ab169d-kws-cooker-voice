# LLM 嵌入式开发规则

本文件放在项目 `.ai/` 目录下，用于约束 LLM 在嵌入式、单片机、RTOS、驱动和板级工程中的代码修改行为。具体可改/不可改文件由 `.ai/LLM_BOUNDARY.md` 定义。

---

## 项目信息

```text
MCU: AB169D (中科蓝讯 Bluetrum)
内核: RISC-V RV32IMAC
时钟: 160MHz max（config.h 配置为 SYS_192M，注意与 Datasheet 标称差异）
Flash: 512KB (AB169D) / 256KB (AB169C)
RAM: 56KB + 16KB Cache
工具链: riscv32-elf-gcc
构建系统: CodeBlocks (.cbp) + riscv32-elf-xmaker 自定义脚本
代码生成器: 无（非 CubeMX/ESP-IDF 类项目）
原理图/硬件文档: reference/schematics/（新旧板分析报告 + 原理图 PDF）
RTOS: 裸机（前后台系统）
```

## 总原则

- 每次执行前必须重新读取本文件和 `.ai/LLM_BOUNDARY.md`，不能只依赖历史上下文记忆。
- 未显式允许修改的文件，默认禁止修改。
- 每次任务必须列出 `Allowed Files`。
- 只做当前任务要求的最小可验证修改。
- 不做顺手重构。
- SDK 平台层（`app/platform/`）中的 BSP/库既有文件默认只读；无代码生成器，不存在复制补齐缺失库的例外。
- 涉及源码、头文件、构建配置、硬件行为、外设、主循环、中断、时序或功耗修改时，必须先输出本轮任务确认单，并等待用户明确确认后再修改文件。
- 可以给出推荐默认方案，但不能把"合理默认值"当作用户确认。
- 需求模糊或缺少关键信息时，必须先向用户澄清后再开发，不得猜测意图、自行假设默认值或选择实现方案。
- 项目存在原理图描述文件或硬件文档时，涉及硬件参数判断时优先阅读 `reference/schematics/` 下的文件，不依赖记忆或猜测。
- 不删除、重排、简化或优化已验证代码。
- 修改后必须给出验证方法、硬件风险和下一步确认点。
- 所有实现遵循 TDD 思路：先定义验证，再实现最小代码，再逐步扩展。
- 添加新功能时，必须创建独立的 `.c` 和 `.h` 文件实现功能逻辑，不允许把业务逻辑直接写在 `main.c` 或已有文件中。`main.c` 中只放函数调用。

## 每轮执行前必检

每次分析、修改、测试或进入下一阶段前，先输出：

```text
已重新读取 LLM_RULES.md / LLM_BOUNDARY.md：yes/no
本轮目标摘要：
```

如果未重新读取规则，或无法确认本轮目标和允许修改范围，不要修改代码。

## 修改前强制确认

只要本轮任务会修改源码、头文件、构建脚本、配置文件或硬件行为，LLM 必须先输出本轮任务确认单，并停止等待用户回复。

确认单固定 5 项：

```text
本轮目标：
Allowed Files：
最小验证方式：
硬件风险：
待确认问题：
```

用户明确回复"确认"、"继续"、"按这个做"或等价表达前，禁止新增、修改、删除文件，禁止调用写文件工具。

如果用户只给出笼统需求，LLM 必须把目标收敛成一个最小可验证功能，并列出可选实现方案供用户确认。

## 项目边界

项目必须维护 `.ai/LLM_BOUNDARY.md`，至少定义：

- 绝对禁止修改的文件和目录。
- 默认允许修改的文件和目录。
- 需要用户单独确认后才能修改的区域。
- 已验证代码和时序敏感代码位置。
- 主入口和主循环保护点。

如果没有 `.ai/LLM_BOUNDARY.md` 或没有定义 `Allowed Files`，LLM 不应修改代码。

## 默认禁止修改范围

除非任务明确允许，不要修改：

- 启动文件（`app/projects/zbit_asr/s_start.S`）。
- 链接脚本（`app/projects/zbit_asr/ram.ld`）。
- 系统时钟配置（`config.h` 中的 `SYS_CLK_SEL`）。
- SDK 平台层 `app/platform/` 中的 BSP/库既有文件。
- 引脚复用和 GPIO 板级初始化（`app/platform/header/io_def.h`、`port_init.c`）。
- ISR 中断服务函数。
- 定时器基础配置。
- 看门狗配置和喂狗点。
- KWS 算法库静态文件（`.a` 文件、算法库 `.c` 文件中的阈值数组）。
- 固件打包配置（`app.xm` 中的 `setauth`、`setuserbin` 地址）。
- 已通过硬件验证的代码。

## 已验证代码保护

以下标记表示代码已经过硬件验证：

```text
VERIFIED_ON_HARDWARE
DO_NOT_TOUCH_TIMING
PRODUCTION_VERIFIED
```

看到这些标记时不删除、不重排、不重构、不合并、不优化、不改变延时和调用顺序。

## main 和主循环保护

向 `main.c` 或主 `while` 循环添加测试代码时，只允许添加带注释的函数调用。

禁止：
- 在 `main.c` 或 `func_run()` 中直接写复杂业务逻辑。
- 删除已有初始化或业务函数调用。
- 为了测试重排已有调用顺序。

临时屏蔽已有调用时，必须备注原因、日期和恢复条件。

## AB169D 专用规则

### 系统配置

- `config.h` 是唯一的系统配置入口（时钟、ASR 参数、外设开关），不要在其他文件重复定义。
- 不随意改动 `SYS_CLK_SEL`（当前 SYS_192M），除非用户明确要求。
- 不随意改动调试口（PA1/2/3、PA4/5/6）配置，避免影响烧录。

### KWS 语音识别

- KWS 核心流水线在 `bsp_asr.c` 的 `asr_sdadc_process()` 中，不要在多个文件分散修改。
- 阈值数组 `KW_TRG_MODE[17]` 在算法库 `.c` 文件中，调整灵敏度只改此数组。
- 命令列表 `kw_string2[17]` 增删时，同步更新 `led_yw.c` 中的 LED 映射。
- `led_ctrl(top)` 如需启用，取消 `bsp_asr.c` 中的注释即可。

### LED 控制

- `led_yw.c` 是 LED 逻辑的唯一入口，颜色/亮度/定时状态机都在此文件。
- 新板（产品板）RGB LED 无串联限流电阻，PWM 占空比不可设为 100%。

### SOP8 引脚资源

- SOP8 封装只有 5 个可用 GPIO，添加新功能前必须检查引脚冲突。
- 引脚分配：Pin4=GREEN, Pin5=RED/W, Pin6=BLUE/Y, Pin8=MIC。

## 外设驱动开发

编写或改写外设驱动时，必须先梳理开发流程并列出缺失信息，等用户确认后再实现。

必须先确认：
- 目标外设型号、数据手册依据（查看 `reference/datasheets/`）。
- 连接方式、引脚、通信参数。
- 初始化流程、API 边界。
- 最小验证步骤。

## 嵌入式基本准则

- 默认 RAM、Flash、CPU、栈空间有限。
- 不在 ISR 中做耗时操作。
- 不随意增加临界区长度。
- I2C/SPI/UART 通信必须考虑超时和错误恢复。
- ISR 与主循环共享的数据必须考虑 volatile 和原子性。
- 编译通过只是最低要求，硬件相关代码必须提供上板验证步骤。
