## 一、这一阶段做了什么？（一句话版）

让芯片**一上电就自动说一句"欢迎使用colorman智能产品"**，然后把这条路（怎么把音频塞进芯片、又怎么放出来）彻底打通——后面的 43 句提示语全靠这条路。

## 二、先扫盲：这一阶段涉及的专业术语（用大白话讲）

| 术语 | 大白话解释 | 类比 |
|---|---|---|
| **Flash** | 芯片里的"硬盘"，断电不丢数据 | 仓库 |
| **code 区** | Flash 里装程序（指令代码）的区域，芯片照着这些指令干活 | 货架上的"说明书" |
| **res 资源区** | Flash 里装"数据"（音频、图片、参数）的区域，程序运行时去拿 | 仓库里的"原料货架" |
| **MP3** | 一种把声音压缩存储的格式 | 压缩饼干（好吃但体积小） |
| **采样率（kHz）** | 每秒"拍快照"记录声音的次数。16kHz=每秒 16000 次 | 每秒拍多少张照片 |
| **码率（kbps）** | 每秒存多少"数据位"。码率越高音质越好、文件越大 | 照片的分辨率 |
| **DAC** | 数字→模拟 转换器。把 MP3 解码出的数字变成电流，推动喇叭发声 | 翻译官（把 0/1 翻译成声音） |
| **res.bin** | 所有音频资源打包后的一个文件，烧进 Flash | 一箱打包好的压缩饼干 |
| **索引表** | 记录"第几号饼干在箱子里第几个位置、多大"的清单 | 装箱单/点名册 |
| **宏（#define）** | 编译时的"文字替换"，让代码好读 | 给数字起外号 |

## 三、核心问题：为什么不能直接把音频"塞进代码"？

### 3.1 芯片很小

AB169D 芯片总共只有 **512KB Flash**（比一张软盘还小）。其中：
- **code 区**：装程序，预算 **292KB**，已经快满了（装上识别引擎后约 291KB）
- 43 条提示语 MP3 加起来 **420KB** —— 比 code 区还大，**根本塞不下**

### 3.2 解决：把音频放到"资源区"，用打包工具管

就像搬家：小物件直接装箱，大件另租仓库。芯片设计者早就留了一个"资源仓库"（res 区），程序运行时按清单去拿。

于是我们的做法是：
```
43 条 MP3 → 压缩变瘦 → 放进 res/ 目录 → xmaker 打包成 res.bin → 烧进 Flash
```

## 四、音频怎么"变瘦"的？（压缩 + 裁静音）

### 4.1 第一步：降低码率

原始提示语是 **16kHz / 32kbps**。我们转成 **16kHz / 8kbps**（码率降 4 倍），文件约小 4 倍。

- **采样率决定"音质上限"**（每秒拍多少张照片）
- **码率决定"文件大小"**（每张照片多清晰）

### 4.2 第二步：裁剪首尾静音

TTS 合成的音频，**开头结尾常有一小段无声空白**（没信息量，纯占空间）。我们量了：每条平均约 **0.4~0.5 秒静音**，占整段时长近 20%！

用 ffmpeg 检测静音 → 裁掉 → 省了约 22% 体积。听感完全无影响。

### 4.3 实测结果

| 项 | 数值 |
|---|---|
| 43 条原始 | 421 KB |
| 压缩后(16k/8kbps) | 120 KB |
| **再裁静音后** | **93.5 KB** ✅ |
| 最终烧录固件 | **475 KB**（上限 496K，安全） |

> 💡 一个反直觉知识点：**降采样率到 8kHz 反而更省不了多少**。因为 MP3 按"帧"打包，每帧有固定开销，低码率时开销占比变大。**码率才是文件大小的主角。**

## 五、关键机制：res 资源是怎么被"点名"取出来的？

### 5.1 打包时生成"点名册"

xmaker 打包 res 目录时，自动生成两个东西：
- **res.bin**：装音频数据本身
- **res.h**：一张"C 代码点名册"，告诉程序每个资源在哪

res.h 长这样（C 代码）：
```c
#define RES_BUF_MP3_RESP01_MP3   (*(u32 *)0x11000038)  // 资源1 的地址
#define RES_LEN_MP3_RESP01_MP3   (*(u32 *)0x1100003c)  // 资源1 的长度
#define RES_BUF_MP3_RESP02_MP3   (*(u32 *)0x11000058)  // 资源2 的地址
...
```

### 5.2 `0x11000038` 是什么？

这是 Flash 映射到内存的一个**固定地址**。程序运行时，**去这个地址读一个数字**，那个数字就是"音频数据在 Flash 里的地址"；再读下一个，就是"这段音频有多长"。

```
固定位置 0x11000038 ──读──→ 得到：音频A 在 Flash 的地址
固定位置 0x1100003c ──读──→ 得到：音频A 有多长
```

好处：**程序根本不用关心资源具体放哪**，运行时照着点名册自取。所以加 43 条资源，代码一行都不用改——加文件、重新打包即可。

### 5.3 规律：点名册是有规律的

第 1 号资源占 0x38，第 2 号占 0x58，第 3 号占 0x78……**每个资源间隔 0x20（32字节）**。

于是播放函数用一条公式定位，不用查表：
```c
#define RESP_BUF_OFFSET(id)  (0x11000038u + ((u32)(id)-1)*0x20u)
```

## 六、播放函数怎么写？（sound_res.c）

```c
void sound_play_boot_welcome(void)   // 上电播欢迎语
{
    dac_spr_set(SPR_16000);   // ① 告诉 DAC：输出采样率按 16kHz
    mp3_res_play(RES_BUF_MP3_RESP01_MP3, RES_LEN_MP3_RESP01_MP3);  // ② 播放资源1
}
```

播放函数 `mp3_res_play(地址, 长度)` 内部会：
1. 初始化音乐解码器
2. 从 Flash 把 MP3 数据流式读出来
3. 解码成数字声音 → 送 DAC → 推喇叭 → 出声
4. 播完自动退出

> 💡 为什么播放前要 `dac_spr_set(SPR_16000)`？
> DAC 是"翻译官"，你得告诉它音频是 16kHz 的，它才能按正确的速度"念"出来。念快了声音变尖、念慢了变粗（这就是变调）。

| `app/projects/zbit_asr/main.c` | 加一行带注释的调用 `sound_play_boot_welcome();` | 上电时触发播放 |

`main.c` 里加在哪？（启动顺序）
```c
bsp_sys_init();            // 初始化硬件（时钟、DAC…）
sound_play_boot_welcome(); // ← 新增：上电播欢迎语
func_run();                // 进入主循环（开始监听唤醒词）
```

> 💡 **为什么在 `func_run()` 之前播？**
> 这时候**麦克风还没开始听**（识别没启动）。如果识别先启动了，喇叭播"欢迎使用..."，麦克风会把这话听进去，万一误判成"你好小柯"就自动唤醒了。**播放和识别错开，就不会互相干扰。**

## 九、这套流程对后面有什么价值？

P1 打通的不只是"一句欢迎语"，而是**一条可复用的流水线**：

```
任意一句提示语 → 转码压缩 → 放 res/ 目录 → xmaker 打包 → 代码里点播
```

P2 就是批量走这条流水线：把剩下 42 句全放进去，再让"识别到的命令"自动点播对应那句。到时候你会看到一个更漂亮的规律：

> 命令编号 1~36（打开火锅…关闭保温）对应的回应语恰好是 **编号 3~38**，因为词表、Excel、资源三个顺序对齐了。所以"命令→回应语"就是一条 **`resp_id = top + 2`** 的加法，连查表都不用。
