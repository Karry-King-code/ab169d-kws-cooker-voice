## 一、项目背景与需求

客户（colorman）要做**陶瓷智能电饭煲**，需求要点：

| 需求项 | 内容 |
|---|---|
| 离线语音 | 唤醒词"**你好小柯**" + 18 类指令（火锅/煮饭/煮粥/煮面/蒸煮/煎炒 + 火力档位 + 预约小时 + 保温 + 取消/暂停等） |
| 语音播报 | 43 条回应语（开机播报/唤醒回答/执行确认/完成播报/纠错） |
| 串口指令 | 识别到的指令通过 **UART 串口**发给客户主控（杰理 AD248B），由主控执行加热/显示 |
| 硬件 | AB169D 语音模块 = 识别 + 播报；加热/显示归客户主控 |

**测试环境**：
- 测试板：ZBIT（板上芯片标注 ZBAAB1PCSJ，SOP8 引脚与 AB169D 数据手册逐脚一致）
- 芯片：用户换上的 **AB169D**（后验证用真 169C/169D 交叉测试）
- 工程基座：ab16x_zba-0322_l124_kws_180k（**v2.0.3**，电灯/化妆镜项目派生）

## 二、阶段一：词库生成与指令表核对

### 2.1 指令表核对（xlsx vs 词库）

客户指令表《智能电煮锅语音控制指令设置》共 61 条。逐条比对后**发现两个缺失**：

- ❌ **"火力调整为四档"**（指令表有，词库没有）
- ❌ **"火力调整为八档"**（指令表有，词库没有）

### 2.2 词库版本迭代

| 版本 | 词数 | 问题 |
|---|---|---|
| 630 (wd77) | 76 | 缺火力四档/八档 |
| 631 (wd79) | 78 | 缺火力四档/八档 + 开机播报 |
| **634 (wd81)** | **37 识别词** | ✅ **最终版**：你好小柯 + 36 命令（含四档/八档）；回应语不在词表（播报走 MP3 资源，不影响） |

最终确认词表 = **80 词**（你好小柯 + 36 命令 + 43 回应语），逐条与客户指令表核对零遗漏。

### 2.3 43 条回应语 MP3 生成

- ttsmaker 生成全部提示语（一个 104 秒的合并文件）
- 用 **miniaudio + lameenc + numpy**（Python）按静音切分：
  - 检测到 ≥0.6s 的停顿正好 42 个 → 切成 **43 段**
  - 每段转成 **16kHz mono 32kbps MP3**（8~14KB/段）
- 43 条回应语与客户指令表逐条对应验证（标点归一化后零缺失）

### 2.4 资源系统修复（重要发现）

**发现**：res.xm 的 `#loadresdir(res)` 多了个 `#`——参考工程的正确写法是 `loadresdir(res)`（无 #）。

```
修复前: #loadresdir(res)  → res.h 永远为空
修复后: loadresdir(res)   → 正常生成 RES_BUF_XXX 宏
```

资源系统修好后，`res/zh/wake.mp3` 能生成 `RES_BUF_ZH_WAKE_MP3` 宏。

## 四、阶段三：语音播报的血泪史（核心）

### 4.1 现象

识别正常，但**喇叭从没出过声**，且一开 DAC 就崩。

### 4.2 完整尝试记录（每一步都有日志/验证）

| # | 尝试 | 结果 |
|---|---|---|
| 1 | `DAC_EN=1` + boot `dac_init`（含 `dac_power_on`） | ❌ boot 崩（停在 `[dac_init]`，后面全没） |
| 2 | boot `dac_init`（跳过 `dac_power_on`） | ❌ 同样崩（定位到 `GPIOADE &= ~BIT(3)` 寄存器写入崩） |
| 3 | 播放时才 `dac_power_on`（boot 不初始化） | ❌ 串口乱码（pin6 被 DAC 抢走 PA2/调试）+ 崩 |
| 4 | 关调试串口（`PRINTF_NONE`） | ❌ 灯不闪（盲测，无日志无法定位） |
| 5 | printf 挪 PA8（跟参考工程同样设计） | ❌ 灯不闪 + 无日志（疑似 printf 初始化前崩） |
| 6 | MP3 嵌入播放（wake 时 `mp3_res_play`） | ⚠️ 播放代码跑完，但**解码立即失败**（`5-decode exit`） |
| 7 | 资源系统修复 + MP3 进资源 | ✅ 资源系统正常（未用于播放） |
| 8 | TEST_DAC 参考工程（v4.0.6，ESBC）编译 | ✅ 编译成功，但**授权码 0x68854D8F 与我们的加密狗 3CC9B441 不匹配**，烧不进 |
| 9 | 参考工程授权码对齐后烧录 | ✅ 烧录成功，但**没声** |
| 10 | 换**真 169C** 芯片测我们 v2.0.3 | ❌ 同样崩在 `[dac_init]` → **证明芯片不是问题**（真 C 也崩） |
| 11 | 换**真 169D** + 参考工程 | ✅ 烧录成功，**没声** |
| 12 | **万用表 AC 档实测** | 🔑 **PA123 复位瞬间有 ~1V AC——DAC 在输出！** |
| 13 | 重新夹好飞线（PA123↔DAC） | 🎉 **出声了！**（kaiji 开机音） |

### 4.3 真相（两层坑叠加）

```
坑1（固件层）: printf 在 PA3 = DAC(PA3) 抢同一个物理脚 pin6
             → 一开 DAC 就崩（GPIOADE 写 PA3 挤掉正在用的调试串口）
坑2（硬件层）: 飞线 PA123↔DAC 接触不良（用手碰 = 时断时续）
             → DAC 输出了但信号到不了 8002 功放

两层叠加 → "怎么试都没声音"，且互相掩盖
```

**关键证据链**：
1. 数据手册：SOP8 **pin6 = PA1/PA2/PA3 同一个物理脚**（三抢一）
2. 我们的 `UART0_PRINTF_SEL = PRINTF_PA3` —— **printf 就在 DAC 脚上**！
3. 参考工程的 printf 在 **PA8**（不在 PA3）——这就是它不崩的原因
4. 万用表实测 PA123 有 AC 电压 —— DAC 在输出，问题在下游
5. 飞线夹牢后出声 —— 物理接触是"一直没声"的隐藏元凶

### 4.4 顺带确认的硬件事实

- **AB169C 和 AB169D 只差 flash**（256K/512K），DAC 硬件完全一样（数据手册 Key Parameters）
- 板上芯片标注 ZBAAB1PCSJ ≠ AB169D（石工确认公司没用过 169D）——但 SOP8 引脚与 AB169D 一致，能跑 AB169D 固件
- 真 C 上我们的固件同样崩在 DAC → 不是芯片个体问题

## 五、阶段四：为什么参考工程一开始不能用

参考工程（TEST_DAC，`ab16x_zba-0287_l112_kws_190k_v4_0_6`）三个拦路虎：

| 拦路虎 | 说明 | 解决情况 |
|---|---|---|
| **① 授权码不匹配** | 参考用 `0x68854D8F`，我们的加密狗是 `3CC9B441` → 烧录报"无效加密狗" | ✅ 已解决：app.xm + xcfg.xm 授权改 3CC9B441 |
| **② flash 装不下** | 参考开 DAC+ESBC 后 260KB > 真 169C 的 256KB | ❌ 物理限制：只能跑 512KB 的 169D |
| **③ 634 与 v4.0.6 跨代际** | 634 是 v3.1.0/180K，参考库是 v4.0.2/190K；API 有差异（`set_kw_enable` vs `set_kw_offset`），帧数不同（2560 vs 384），链接缺 `__ashrdi3` | ⚠️ 适配后能编译，但运行时异常（滴答声+LED 乱跳） |

**结论**：参考工程是"探路石"（证明芯片能出声 + 揭示 printf 正确位置），但不能直接作为电饭煲基线（词库不匹配 + 授权/容量问题）。

## 六、阶段五：A2 方案——为什么现在可以了

### 6.1 思路转变

```
之前：在新基线(v4.0.6)上适配我们的东西 → 跨代际风险
现在：回到 v2.0.3（634 本来就配对、识别已验证）
     + 借参考工程的"printf 挪 PA8"设计
     + 修复物理飞线
```

### 6.2 A2 的三步修复

| 步骤 | 改动 | 目的 |
|---|---|---|
| ① | `UART0_PRINTF_SEL: PRINTF_PA3 → PRINTF_PA8` | pin6 完全让给 DAC，boot 不再崩 |
| ② | `DAC_EN=1` + `WARNING_TONE_EN=1` + `WARNING_MP3_PLAY=1` | 开启音频通路 |
| ③ | `sound_res.c` 嵌入"我在请问有什么需要"MP3，识别到 top==0 播放 | 唤醒播报 |
| + | 飞线夹牢 | 物理通路修复 |

### 6.3 为什么现在有把握（验证链完整）

```
① 真169D + 参考工程(v4.0.6, DAC+ESBC) → 出声 ✅
   （证明：芯片DAC ✅ / 功放8002 ✅ / 喇叭 ✅ / 飞线通路 ✅）
② v2.0.3 + 配对634 → 识别上板验证过 ✅
③ printf 挪 PA8 → pin6 冲突消除（参考工程同样的设计）✅
→ A2 = ② + ③ + 已验证的音频通路 = 理论完整
```

### 6.4 为什么参考工程移植 634 不行（对比）

| 项 | v4.0.6 + 634（不行） | v2.0.3 + 634（行） |
|---|---|---|
| 库代际 | 跨代际（v3.1.0 vs v4.0.2） | 配对（同代） |
| API | set_kw_enable vs set_kw_offset 差异 | 天然一致 |
| 帧数 | 2560 vs 384 不匹配 | 天然 384 |
| 运行时 | 滴答声+LED 乱跳（不稳定） | 识别正常（验证过） |

## 八、关键发现总结

1. **SOP8 pin6 = PA1/PA2/PA3 同一个物理脚**——DAC(PA3)/调试串口(PA2)/MICBIAS(PA1) 三抢一，这是所有崩溃的根源
2. **printf 位置决定 DAC 生死**——printf 在 PA3 = 开 DAC 必崩；挪 PA8 = 相安无事
3. **C/D 只差 flash**——同 SDK 理论通用，验证了芯片不是问题
4. **飞线接触不良**——DAC 一直在输出，只是信号到不了功放（万用表破案）
5. **资源系统 `#` bug**——`#loadresdir` 应为 `loadresdir`
6. **授权码/加密狗绑定**——不同产品授权码不能互烧
7. **跨代际 KWS 库不可混用**——180K(v3.1.0) 塞进 v4.0.6 框架不稳定

### 阶段六：烹饪流程自动播报（2026-08-31）

**需求**：识别"打开煮饭/煮粥/煮面/蒸煮"后自动定时 10 秒 → 播"已结束，进入保温状态"（resp44）→ 进入保温，5 秒后播"保温已结束，欢迎下次使用"（resp45）；识别"打开保温"直接进保温（5 秒）。倒计时可打断。

**实现**（`led_yw.c` 烹饪流程状态机 `cook_state_t`）：
- 词表 index：煮饭=10、煮粥=12、煮面=14、蒸煮=16、打开保温=35、关闭保温=36
- 识别命令（经 `led_ctrl`）→ `cook_flow_cmd()` 更新状态；`led_loop()` 每帧 `cook_flow_process()` 用 SDK `tick_get/tick_check_expire` 倒计时
- 到点 `sound_request(44/45)` 异步播报（复用 sound_poll 主循环机制）
- `sound_res.c` 播报上限 43→45；`RESP_BUF_OFFSET` 公式不变（每项 0x20）

**插曲（版本教训）**：该功能最初误做在旧提交 b74866c（游离 HEAD）上；发现后备份 → `git checkout main`(3c11c79 音质统一版) → 重放全部代码与音频。两个版本的差异：内嵌 wake_mp3 删除（唤醒走 resp02）、43 条重编码为 -18.6dB 响度线。**教训：开工前先确认 HEAD 在 main 且工作区干净。**

**音频（按 main 统一规格重转）**：resp44/45 = 24kHz wav → 16kHz mono 8kbps MP3 + volume 增益(+2.0/+2.1dB 含编码损耗补偿)，实测 mean = **-18.6dB**，与 main 上 43 条完全一致。源 wav 在 `reference/wav/tick/`。

**烧录**：main 基线 app.dcf=480447(469.2K)，加 resp44/45 后预计 ~477K < 496K 上限，余量约 19K（待编译后实测确认）。烧录用 app.dcf。
